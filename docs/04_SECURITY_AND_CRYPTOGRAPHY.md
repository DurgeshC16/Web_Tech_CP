# 04 — Security & Cryptography

## 1. Cryptographic design

### 1.1 Canonical certificate digest

Every identity field **and** the file are bound into one SHA-256 digest
(`CryptoService::computeCertificateHash()`):

```
h = SHA-256( certificate_id | institution_id | student_id | title |
             issue_date | expiry_date | SHA-256(file bytes) )
```

`|` is a literal pipe. `title` is the only free-text field; all others are
identifiers or ISO dates that cannot contain `|`, so the encoding is
unambiguous (200 000 random title/date combinations produced no collision —
see doc 08). The expiry date is inside the digest, so extending a validity
period requires a fresh signature.

### 1.2 Digital signature

```
σ = RSASSA-PKCS1-v1_5-Sign( sk_institution , hex(h) )   — OpenSSL, SHA-256
```

* RSA-2048 key pair per institution, generated by the super admin's
  approval action (`super_admin.php`).
* The 64-character hex string of `h` is signed (so the signed value is a
  hash of a hash). Signatures were cross-checked with the OpenSSL CLI and
  an independent Python implementation (100/100 verified).
* Signing ≈ 1.09 ms, verification ≈ 0.35 ms (single vCPU) — cheap for a
  read-heavy workload.

### 1.3 Private-key storage

* Wrapped with **AES-256-GCM** (96-bit random nonce, 128-bit tag), format
  `GCM1.base64(iv ‖ tag ‖ ciphertext)`.
* Wrapping key = `SHA-256(APP_ENCRYPTION_KEY)`. **Set `APP_ENCRYPTION_KEY`
  before the first institution is approved**; changing it later orphans all
  stored keys.
* Legacy AES-256-CBC blobs from early builds are still readable.
* After decryption the key must parse as a PEM and match the stored public
  key (`verifyKeyPair()`) before it is used.
* External-source credentials are stored the same way (`CFG1.` blobs).

### 1.4 Versioned keys and fingerprints (migration 012)

* Each certificate records the `key_id` that signed it. Rotating a key
  retires the old version but keeps it, so historical certificates keep
  verifying.
* Public-key fingerprints (`SHA-256` of the PEM, colon-hex) are shown on the
  verify page and published at `institutions.php` and
  `/.well-known/certivault-keys.json` so verifiers can compare them through
  an independent channel.

### 1.5 Transparency log (opt-in, `CERTIFICATE_TRANSPARENCY_ENABLED`)

* Issue, revoke and supersede events append a leaf
  `SHA-256(certificate_id | sha256_hash | signature | created_at)` to
  `tlog_entries`.
* Merkle tree with RFC 6962 / RFC 9162 leaf/node domain separation;
  inclusion proofs ≤ ⌈log₂ n⌉ hashes (≤ 640 bytes at 10⁶ records).
* `scripts/publish_checkpoint.php` signs the root with a **separate**
  platform key (`private_data/tlog/`) and writes
  `public/checkpoints/latest.json`. Publishing that file somewhere CertiVault
  cannot write to (e.g. a separate GitHub repo) makes silent edits to
  history detectable with `scripts/compare_checkpoint.php`.

## 2. Verification cascade

Order (fixed; status first because it is server-authoritative):

```
exists? ── no ──► INVALID
   │
revoked? ── yes ─► REVOKED
superseded? ─ yes ► SUPERSEDED (+ link to the current version)
recomputed h == stored h? ── no ──► TAMPERED   (data or file altered)
RSA verify(h, σ, pk)? ────── no ──► TAMPERED   (forged / wrong key)
expired (status or date)? ── yes ─► EXPIRED
                                    VALID
```

All 16 combinations of status × integrity × expiry were checked against an
independent oracle (doc 08).

## 3. Security controls

### Authentication & sessions

| Control | Implementation |
|---------|----------------|
| Password hashing | bcrypt (`password_hash`), strength rule 8–72 chars with upper, lower, digit, special |
| Login lockout | 5 failed attempts per email + IP within 15 min → locked until the window passes |
| CAPTCHA | Google reCAPTCHA v2 when keys are configured, otherwise an offline arithmetic CAPTCHA (login, both registrations, forgot password) |
| Email OTP | 6-digit codes stored as HMAC-SHA-256 with `OTP_PEPPER`; 10-min lifetime; 5 wrong attempts invalidate the code; 60-s resend cooldown; 5 codes/hour |
| Sessions | HttpOnly, SameSite=Strict, Secure on HTTPS; ID regenerated at login and password change; 30-min idle and 8-h absolute timeout |
| Remember me | 30-day `selector:validator` cookie; only SHA-256(validator) stored; tokens revoked on password change |
| Logout | POST + CSRF only (a prefetched GET cannot log you out) |

### Authorization

* `require_role()` on every protected page (also enforces session timeouts
  and `no-store` cache headers).
* `require_approved_institution()` — pending/rejected institutions cannot
  issue anything.
* `require_owned_certificate()` — row-level ownership for view, download,
  revoke and supersede.

### Input handling & web hardening

| Threat | Control |
|--------|---------|
| SQL injection | PDO prepared statements everywhere, emulation off; identifiers never come from input |
| XSS | `htmlspecialchars()` on all output; CSP |
| CSRF | Per-session token on every POST form |
| Malicious uploads | Extension **and** `finfo` MIME must agree (PDF/PNG/JPEG); 100 B – 5 MB; stored outside web root under random names; served only through `download.php` with `nosniff` |
| Enumeration of IDs/tokens | 256-bit tokens; > 30 distinct lookups per IP per 10 min → HTTP 429; all lookups logged |
| SSRF (external sources) | HTTPS only, host allow-list, every resolved IP must be public, redirects re-validated, 5 s timeout, 1 MB cap |
| Look-alike issuer links | Exact-host matching; typosquats / punycode shown as warnings, never as links |
| Clickjacking / sniffing | `X-Frame-Options: DENY`, `frame-ancestors`, `X-Content-Type-Options: nosniff` |
| Info leakage | `Referrer-Policy`, `Permissions-Policy`, HSTS on HTTPS, errors logged to `private_data/php_errors.log` not displayed |
| Direct file access | `private_data/.htaccess` denies all; services live in `src/` outside the web root |
| Committed secrets | Production guard refuses to boot (`CV_ENV=production`) while `APP_ENCRYPTION_KEY`, `OTP_PEPPER` or `SHARE_LINK_SECRET` still have their development defaults |

### Share links

`share.php?token=` carries `base64(payload).HMAC-SHA-256(payload,
SHARE_LINK_SECRET)` with an integer certificate ID and a 24-hour expiry.
`SHARE_LINK_SECRET` is separate from the encryption key so a leak of one does
not compromise the other.

## 4. Threat model

Attackers ordered by capability, with what stops them:

| Adversary | Can do | Stopped by |
|-----------|--------|-----------|
| Stranger with a PDF copy | Edit the file | File hash inside the signed digest → TAMPERED |
| Storage writer | Replace/alter stored file | Same → TAMPERED |
| DB writer (not key table) | Edit fields, recompute digest | Signature no longer matches → TAMPERED |
| DB writer re-signing with own key | Forge with attacker key | Verification uses the issuer's stored key → TAMPERED |
| DB writer **incl. key table** | Swap the institution's public key and re-sign | **Not stopped by the core design.** Mitigation: compare published key fingerprints / pin them outside the DB |
| Silent history edit | Change or delete issued records | Merkle transparency log + externally anchored checkpoints |
| Dishonest approved institution | Issue a false certificate | Not preventable by cryptography — approval gate and audit trail only |

## 5. Known security gaps

* **CSP allows `'unsafe-inline'`** for scripts and styles (inline helpers
  and `style=` attributes); a nonce refactor is needed (doc 09).
* **Key pinning is not enforced automatically** — fingerprints are
  published, but the verifier does not yet compare against a pinned copy
  outside the database.
* **Single operator** — availability and trust rest on one server.
* **Repo-root exposure in dev setups** — if the *repository root* (not
  `public/`) is served (e.g. cloned straight into `htdocs` or
  `php -S` without `-t public`), files such as `database/schema.sql` or
  `.git/` become reachable. Always serve `public/` only (doc 06).
